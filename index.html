先看市场：岗位到底在招什么

以下结论基于 2026-09-07 检索到的代表性公开职位与技术团队资料。具体职位会下线，因而将它们作为能力模式样本，而不是永久岗位清单。

结论：当前市场对“模型开发”的定义，通常是“模型 + 数据 + 评测 + 系统集成”四件事的闭环。 单独会调一个开源 VLM，或者只会复现一个公开 benchmark，都不足以覆盖岗位要求。VLM/世界模型岗位的门槛更高，通常建立在自动驾驶感知、规划或大规模 foundation-model 训练经验之上。

先建立系统地图：模型位于哪一层

智能驾驶不是单一模型问题。即使最终采用端到端策略，传感器、坐标系、状态估计、数据闭环、评测与 safety envelope 仍然存在。

flowchart TD S["传感器
camera · lidar · radar · IMU · GNSS"] --> C["标定与同步
坐标变换 · ego motion · time alignment"] C --> P["环境表征
2D/3D detection · tracking · BEV · occupancy"] P --> F["预测与规划
agents · map · route · trajectory"] F --> A["控制与执行
vehicle dynamics · controller · actuation"] P --> Q["质量与安全
OOD · uncertainty · rules · fallback"] F --> Q Q --> A D["数据闭环
mining · labeling · replay · simulation"] --> C D --> P D --> F

模块化栈

每层有显式接口，便于定位错误、验证安全约束、逐层替换。适合先学习和做工程作品。

端到端栈

将多个层的映射统一为 policy，可能减少接口损失并提高数据驱动能力，但误差归因、分布外泛化和闭环评测更困难。

混合栈

用神经模型提供表征或候选轨迹，用几何/规则/控制器提供约束与 fallback。当前很适合作为学习和落地的中间形态。

你已有深度学习基础，还需要补哪些“非 DL”能力

不建议重新完整学习一遍深度学习。你的边际收益主要来自几何、时序、车辆/机器人系统和安全评测。

知识块需要达到的工作级理解暂时不必深挖验证方式
线性代数 / 概率坐标变换、协方差、概率轨迹、多模态分布、NLL/Calibration。从头证明所有优化器；与项目无关的泛函分析。能解释预测分布与置信度如何进入 planner。
多视几何针孔模型、内外参、畸变、三角化、PnP、SE(3)、ego motion。暂不需要先做完整 SLAM 系统。能从传感器坐标投影到 camera/BEV，并定位错位来源。
时序建模causal attention、tracking、运动补偿、memory、action/trajectory horizon。不必先追逐所有长上下文 LLM 结构。能做 Δt、遮挡、历史长度的 ablation。
车辆与控制bicycle model、curvature、速度/加速度/jerk、轨迹可行性、MPC 基本接口。暂不需要先研究完整车辆动力学仿真。能判断模型轨迹是否物理可执行。
软件与部署Python 训练 + C++ 推理接口、数据并行、profiling、量化、显存/延迟预算。不必一开始学习整套车载中间件。把一个模型导出/编译并给出 p50/p95/p99。
安全与验证scenario taxonomy、OOD、uncertainty、fallback、闭环/非闭环差异。不把法规阅读当作算法入门主线。能设计 critical-event recall 与回归门禁。

VLM、VLA、WA、World Model、π0：不要混成一类

术语边界仍在演化；尤其是 WA/WAM 在不同公司和论文中可能有不同含义。下面给出面向学习和求职的工作定义。

名称输入 / 输出主要解决的问题在智能驾驶中的位置
VLM
Vision-Language Model		 图像/视频 + 文本 → 文本或结构化语义 视觉理解、描述、问答、开放词汇识别、语义推理。 可作为 scene understanding、长尾语义、数据标注/检索、规划条件生成器；不等于直接控制车辆。
VLA
Vision-Language-Action		 视觉/语言/状态 → action、waypoints、trajectory 或控制量 把语义条件与可执行行为统一起来。 可用于端到端驾驶或高层决策；必须补充时序、几何、车辆动力学和安全约束。
WA / WAM
World Action / World-Action Model		 视频/多模态历史 + action → 未来世界状态/视频 latent 与 action 利用视频 foundation model 的运动连续性和场景演化先验，减少对语言中间层的依赖。 适合研究未来场景生成、counterfactual、轨迹规划与联合 world-action policy。该缩写未形成统一标准。
World Model 历史观测和 action → 未来状态/观测/latent dynamics 学习环境如何演化，从而支持预测、规划、仿真或数据生成。 可以是视频、3D geometry、occupancy、latent 或多传感器生成模型；不必输出语言，也不一定直接输出 action。
π0 / PI VLM 表征 + 连续 action expert，通常生成 action chunk 将通用视觉/语言知识接到高频、连续、精细的机器人控制；PI 后续工作还覆盖动作 token 化、异步执行、部署经验学习和 memory。 主要是机器人 VLA 研究。对智驾最有价值的是 action representation、时延隐藏、异构数据训练和部署后学习方法，而不是直接照搬 action space。
WA 的说明：本文把 WA/WAM 按当前自动驾驶和机器人文献中常见的 World-Action Model 理解；它不是统一的行业标准名词。DriveWAM 将预训练视频 foundation model 适配为联合视频-动作策略；NVIDIA 对 WAM 的综述也将其描述为视频/世界模型 backbone 与 action policy 的交叉路线。对公司 JD 应以该公司的具体定义为准。

26 周路线：先补智驾背景，再进入 L4 主干

默认每周 12–18 小时；如果全职投入，可压缩到约 14–16 周。每个阶段都必须有可运行的代码、指标和失败分析，不以“看完课程”为完成条件。

第 1–2 周 · AD domain bridge

先学会读懂自动驾驶系统

  • ego、actor、scene、ODD 和 perception/tracking/prediction/planning/control 接口。
  • camera/LiDAR/radar/GNSS/IMU、坐标系、时间戳和 ego-motion。
  • BEV、occupancy、vector/map、agent state 的表示选择。
  • 用 6 个 bridge notebook 完成领域 checkpoint，不重复通用深度学习。
第 3–4 周 · ODD、几何与系统契约

先写系统契约

  • ODD、模块输入输出、坐标系和时间预算。
  • SE(3)、相机模型、投影、ego motion。
  • Linux/Git/Docker、PyTorch 数据管线。
  • 为一次 sensor bundle 写 contract validation。
第 5–7 周 · 3D 感知

从 2D 进入 BEV/3D

  • 2D/3D detection、tracking、segmentation。
  • LiDAR voxel/point、camera depth、BEV。
  • 在 MMDetection3D/OpenPCDet 跑通 baseline。
  • 做一次数据和坐标错误排查。
第 8–10 周 · 融合、时序与定位

让模型看见同一个世界

  • camera-LiDAR BEVFusion 和 PyTorch Transformer。
  • 时间同步、外参误差、遮挡和 modality dropout。
  • temporal memory、ego-motion compensation、GNSS/IMU/map matching。
  • 报告 accuracy–latency–robustness trade-off。
第 11–14 周 · 预测、规划与闭环

从看见到可执行轨迹

  • 轨迹预测、交互、多模态分布。
  • 行为规划、轨迹生成、车辆运动学和约束。
  • nuPlan/NAVSIM 的 log replay、open-loop 和 closed-loop 评测。
  • 理解 rule-based、hybrid、learning planner。
第 15–17 周 · 场景与数据闭环

让错误可以被重复测试

  • scenario contract、log replay、reactive agents。
  • 场景 taxonomy、数据挖掘、hard negative、active learning。
  • collision、off-road、comfort、fallback latency 和 scenario coverage。
  • 把每个 failure 变成 regression case。
第 18–20 周 · 安全与部署

让模型能被安全地发布

  • ODD exit、fault monitor、degraded mode、minimal-risk maneuver。
  • 规则 monitor 与 learned policy 的独立性。
  • ONNX/TensorRT 或等价 runtime、p50/p95/p99、watchdog。
  • 报告安全、鲁棒性和实时性的联合 trade-off。
第 21–23 周 · E2E 与驾驶 foundation

统一 perception–prediction–planning

  • 阅读 TransFuser、UniAD、VAD/VADv2、GenAD。
  • 做 camera-only waypoint policy 或轻量驾驶 Transformer。
  • 加入 uncertainty、collision、comfort 和 route condition。
  • 解释为什么 open-loop L2 不是安全结论。
第 24–26 周 · 前沿与求职

把 VLM/VLA 接到 L4 接口

  • HF VLM、Diffusion、Robotics 课程。
  • LeRobot、OpenVLA、Octo、openpi。
  • VLM scene reasoning → structured driving condition。
  • 完成 L4 capstone、整理 repo、实验表、失败案例和面试证据。
持续循环 · 数据飞轮

形成自己的研究问题

  • 每次错误都归类为 perception、data、temporal、planning、system 或 safety。
  • 每个改动都保留 ablation 和回归结果。
  • 每月追踪公开 JD 与新 benchmark。

P2 · Fusion Robustness 做 camera dropout、LiDAR dropout、外参扰动、时间错位、雨夜或低能见度的鲁棒性实验。 BEVFusion、nuScenes、CARLA 可补充合成扰动 性能退化曲线、uncertainty、fallback 策略、哪种 fusion 机制更稳定。
P3 · Prediction + Planning 用 agent history、map/route 和 ego state 预测多模态轨迹，并用简单 planner 生成自车 waypoint。 Waymo Motion、nuPlan、NAVSIM minADE/minFDE/miss rate/NLL、collision/TTC、progress、comfort、闭环差异。
P4 · Corner-Case Safety Layer 设计小模型 + 规则 monitor：检测遮挡行人、施工锥桶、异常静止物、传感器退化等事件，并决定继续、降速、切换候选或 safe stop。 CARLA、SafeBench、Waymo challenges、nuPlan 事件召回率优先的指标、误报代价、TTC/碰撞、fallback latency、场景覆盖矩阵。
P5 · VLM/WA/π0 Bridge 先让 VLM 输出结构化 scene summary/route condition，再接 waypoint head；或以视频模型预测 future latent 与 action chunk，和普通 policy 做对照。 HF VLM course、LeRobot、OpenVLA、openpi、DriveWAM 语言/视觉条件的可控性、时序一致性、轨迹安全、推理 latency、失败模式；明确声明不是完整量产智驾。
项目组合建议：如果只能做三个，做 P0 + P1/P2 + P3/P4；如果希望申请 foundation-model 或具身/智驾交叉岗位，再加 P5。P5 不能替代 P0–P4。

多传感器融合：最容易被论文名词遮住的基本功

融合的核心不是把 tensor concat 起来，而是把来自不同坐标系、时间、噪声模型和可见性条件的观测映射到一致的时空状态。

1. 先把坐标和时序做对

设传感器 (s) 在时刻 (t_s) 观测到点 (x_s)，车体坐标系为 (e)，世界坐标系为 (w)。基本变换为：

\[ x_e(t_s)=T_{e\leftarrow s}x_s(t_s),\qquad x_w(t_s)=T_{w\leftarrow e}(t_s)x_e(t_s) \]

若相机和 LiDAR 的时间戳不一致，直接把 (x_s(t_s)) 与 (x_c(t_c)) 融合会产生运动目标错位。需要通过 ego pose、速度或连续轨迹做 motion compensation；静态场景也需要检查采集系统的 timestamp 语义。

\[ u\sim K\,[R\mid t],x_e,\qquad p_{\mathrm{BEV}}=\Pi\bigl(x_{\mathrm{camera}},x_{\mathrm{lidar}},T,K,\Delta t\bigr) \]

2. 四种融合层次

层次方式优点主要风险学习重点
Early fusion原始点、图像或投影后的低层特征直接融合信息交互充分强依赖标定、同步和分辨率对齐坐标、投影、数据质量
Feature fusion各模态编码后在 BEV/voxel/query 层交互可分别学习模态结构，代表当前主流模态缺失、特征尺度和 attention 偏置BEV、cross-attention、dropout/robustness
Late fusion各模态先独立预测，再合并结果易于替换和故障隔离跨模态互补信息利用不足不确定性、calibration、ensemble
State/trajectory fusion在 tracking、prediction 或 planning 状态层合并接口清晰、可与规则和控制器结合上游错误传播，信息已压缩状态估计、时序一致性、安全约束

3. 你必须做的四个 ablation

Modality dropout

随机或按场景移除 camera/LiDAR/radar，观察模型是否 graceful degradation，而不是直接失效。

Calibration perturbation

对 (T_{e\leftarrow s}) 注入平移/旋转误差，画性能与几何误差曲线。

Temporal misalignment

注入 (Delta t)，尤其观察高速目标、切入车辆和行人类别的退化。

Uncertainty / quality head

输出置信度、遮挡或传感器质量，供上层 monitor、fallback 和数据挖掘使用。

Corner Case：规则不是“落后方案”，而是安全接口

在安全关键系统中，corner-case 处理通常不是“再训练一个万能大模型”这么简单，而是数据挖掘、轻量检测、确定性约束、fallback 和闭环评测的组合。

flowchart LR O["多模态观测"] --> M["主模型
perception · prediction · planning"] O --> D["质量/异常小模型
OOD · sensor health · event detector"] M --> R["规则与安全 monitor
TTC · drivable area · hard constraints"] D --> R R --> E["继续执行 / 降速 / 候选切换 / safe stop"]

适合学习者实现的 hybrid 设计

observation ├── main_policy(observation, route) -> trajectory_candidates ├── quality_model(observation) -> {ood, sensor_health, event_score} └── rule_monitor(candidates, map, dynamics, risk) -> decision decision: if critical_event and confidence_low: fallback_to_safe_trajectory() elif collision_risk or hard_constraint_violation: reject_candidate_and_replan() else: execute_with_controller()
层适合使用规则的地方适合使用小模型的地方不要把什么交给单一层
感知质量传感器掉线、时间戳异常、输出越界、几何一致性遮挡/天气/异常物体/长尾事件识别不要用规则替代所有语义感知
轨迹筛选碰撞、道路边界、动力学、最小 TTC、硬约束候选风险排序、交互难度预测不要只用 open-loop L2 选择安全轨迹
运行时超时、显存不足、模型版本回归、safe stop异常行为分类、故障归因不要用“置信度高”直接等价于安全
数据闭环规则化 scenario query、覆盖统计、回归门禁难例检索、相似场景聚类、优先级预测不要只根据平均指标决定采样
安全评测原则：对 critical event，通常应优先控制 false negative；AUROC、平均准确率或全局 mAP 只能作为辅助。你需要报告事件召回率、误报代价、TTC、碰撞/越界、fallback 延迟和场景覆盖，而不只是一个模型分数。

你的第一周：不要从论文列表开始

第一周的目标是产出一个能运行的 sensor-to-visualization pipeline，并建立个人术语表。

  1. 安装 Linux/Docker、PyTorch、OpenCV、numpy、三维可视化工具和一个 Git 仓库。
  2. 阅读 MIT 16.485 中关于坐标系、投影、SE(3) 的材料，手写并测试 (T_{a\leftarrow b}) 的组合与逆。
  3. 下载 nuScenes mini，画出同一时刻的多视角 camera、LiDAR、3D box 和 ego pose。
  4. 人为修改外参和时间戳，确认你能看到投影/融合错误。
  5. 建立 `glossary.md`：每个词都写输入、输出、坐标系、指标和失败模式；第一批包括 BEV、occupancy、tracking、NDS、TTC、OOD、fallback、VLM、VLA、WAM。
  6. 把第一次运行记录成 issue：环境、命令、输出、失败原因和修复方式。
判断是否可以进入下一阶段：你能在没有复制粘贴模型代码的情况下解释一条 3D box 是如何从传感器坐标系变换到车体/世界/BEV 坐标系的，并能指出时间错位、外参错误和标签错误分别会如何影响模型训练。
